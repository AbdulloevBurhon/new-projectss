## Как мы работаем

- Пользователь описывает ожидаемый результат и может приложить скриншоты. ИИ сам ищет причину, меняет код и проверяет результат по обычному сценарию. Подписи на макете служат контекстом к запросу.
- Проследи цепочку «страница → компонент → клиентский запрос → обработчик → данные». Переиспользуй таблицы, пагинацию, кнопки и диалоги проекта. Раскладывай код по назначению и держи исходные файлы фич короче 120 строк.
- Склад, счета, продажи, сотрудники и клиенты используют локальную SQLite. В Nuxt запросы идут через `tsekh/server/api/` и `tsekh/server/services/`. Windows EXE обслуживает те же прикладные маршруты через `tsekh/desktop/`. Общие SQL-запросы находятся в `tsekh/server/database/`. Облачный API находится в `cloudflare/worker/`, админка — в `admin/`. Часть данных, в том числе техкарты, хранится в браузере или WebView.
- При изменении прав проверяй и видимость действий в интерфейсе, и доступ на сервере. При изменении продажи или поступления сверяй связанные остатки, операции счёта и историю по тестовым данным. При изменении общего API проверь обработчики Nuxt и Windows.
- Для локального запуска из корня есть `npm.cmd run dev:tsekh`. Если сервер уже запущен, используй его адрес. Пользователь попросил **не запускать сборку**. Выбирай подходящие проверки через dev-сервер, тестовую SQLite и проверку изменённых файлов. В отчёте указывай, что проверено фактически.
- При изменении поведения обновляй инструкцию раздела. В каждом затронутом `CHANGELOG.md` добавляй сверху дату, изменение и фактическую проверку. Старые записи и чужие изменения сохраняй.

## Где остановились

- В списке продаж остаток показывается до двух знаков после запятой, например `12,87 уп`. В карточке Telegram время показывается до минуты. Расчёты используют исходные значения.
- Прежний Cloudflare Worker ожидал текст сверки. В коде добавлено согласование формата. Прежний сервер получает JSON-бэкап и текст, обновлённый Worker отправляет три сообщения с файлами: полный JSON-бэкап, отчёт по продажам и остатки ниже 50 шт. или 50 кг по складам. Ровно 50 в отчёт не входит.
- В коде реализована отправка по расписанию, пока «Цех» открыт под администратором или сотрудником. Администратор сохраняет интервал на рабочем устройстве, сервер выдаёт ключ только для отправки на подтверждённый чат. Сотрудник запускает очередную отправку без доступа к настройке и выгрузке базы. Порог остатков применяется при формировании отчёта по расписанию.
- Проверены шаблоны Vue, тестовая SQLite, маршруты сотрудника, три файла через имитацию Telegram API, отзыв ключа и форматы прежнего и нового Worker. Рабочий Worker не обновляли, реальная доставка и Windows EXE после правки не проверялись.
- Чтобы включить расписание для сотрудников в рабочей установке, в согласованной выкладке применить миграцию `0009_telegram_background.sql` и развернуть обновлённый Worker. Затем администратор один раз нажимает **«Сохранить интервал»** на рабочем устройстве. Точки входа и диагностика описаны в [инструкции Telegram](docs/features/telegram.md).
