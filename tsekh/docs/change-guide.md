# План изменения и проверки

[Главная карта](../STRUCTURE.md)

## Добавление или исправление

1. Найди пользовательский сценарий и ожидаемый итог в инструкции раздела. Определи, что должно измениться на экране, в данных и в связанных разделах.
2. Проследи цепочку от `app/pages/` через компонент и API до хранилища. Для существующей операции начни с её текущего обработчика и типов. Для маршрута, который работает в EXE, проверь диспетчер `desktop/WorkshopApi.cs` и соответствующие модули.
3. Оставь страницу тонкой. Размещай UI в `components/`, состояние экрана в `composables/`, контракт в `endpoints/`, проверку входных данных и прав на сервере. Разделяй файлы по ответственности по мере роста, сохраняя лимит проекта.
4. Для таблиц используй общую таблицу раздела или компонент `@obshaya/ui`. Передавай фильтрованные строки, используй предоставленную пагинацию и сбрасывай страницу при смене фильтра. Для кнопок и диалогов используй существующие компоненты и стили.
5. При изменении данных продумай старые записи, повторный запрос и частичный сбой. Связанные складские и денежные изменения выполняй одной транзакцией. При изменении схемы проверь миграцию и импорт действующего формата архива.
6. Обнови инструкцию фичи, а при изменении маршрута обнови карту. В конце каждой задачи обнови журнал каждой затронутой фичи. Для новой фичи создай `CHANGELOG.md` и добавь ссылку на него в карту.

## Что проверить до сдачи

| Изменение | Проверка |
| --- | --- |
| Вёрстка, формы и таблицы | Открыть нужный маршрут. Проверить первый экран, пустой список, реальные строки, фильтр и переход между страницами. |
| Поступление, продажа, счёт | Использовать тестовые товары и счета. Сопоставить значения до и после операции в UI, ответе API и SQLite. Проверить отказ при недостаточном остатке или балансе. |
| Права | Выполнить сценарий со всеми требуемыми правами и с ограниченной ролью. Сверить, что сервер отклоняет запрещённую операцию. |
| API, SQL или архив | Проверить Nuxt и Windows, если операция используется в обоих. Для архива выполнить экспорт и импорт в отдельную тестовую базу. |
| Облако и Telegram | Проверить подтверждение, штатную доставку и отсутствие сети на тестовой установке. Для проверки внешней отправки использовать согласованного получателя и тестовые данные. |
| Только документация | Проверить ссылки, пути, актуальность маршрутов и `git diff --check`. |

Запуск сборки и выкладку выполняй в рамках задачи и с учётом текущих указаний пользователя. В результате перечисли проверенные сценарии и укажи, какое окружение использовано.

## Как поручить задачу ИИ

Можно описать проблему обычными словами и приложить скриншот. Пример задания:

> Открой карту «Цеха» в `tsekh/STRUCTURE.md` и инструкцию нужного раздела. На экране «История» меняю счёт у проведённого прихода. В истории нового счёта нет списания. Воспроизведи на тестовых данных, найди причину и исправь. Проверь остаток и детали обоих счетов. В ответе укажи причину и результат проверки. Сборку не запускай.

Для новой функции достаточно описать экран, что делает пользователь, какой результат должен увидеть и какие данные должны сохраниться. ИИ по карте найдёт файлы, определит связанные экраны и выберет проверки. Скриншоты и сообщения об ошибках дополняют описание сценария.

## Как вести журнал фичи

Добавляй записи сверху, под заголовком. Формат — `- ГГГГ-ММ-ДД — что изменилось и как проверено.` Если задача была диагностикой, укажи симптом, найденную причину или текущий вывод и фактический результат проверки. Если задача затронула несколько фич, добавь в каждый журнал запись о последствиях для своего раздела. Сохраняй старые записи.
